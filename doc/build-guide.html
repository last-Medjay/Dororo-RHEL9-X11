Dororo Project Manual No. I — Building from Source

Building Dororo from Source on RHEL 9 — Beginner's Guide

This guide walks you through building Dororo for RHEL 9 from scratch. No Godot, Live2D, or C# experience required — every step is explained, every command is given verbatim. Expect ~1–2 hours including downloads.

If you just want the pre-built binary, skip this and use the deployment tarball plus README-RHEL.md in the export/ folder.

1. What is Dororo?

Dororo is a desktop pet — a small animated Live2D character (Doro) that floats on your desktop in a transparent window. You can drag her around, she follows your cursor with her gaze, plays expressions, and interacts with mouse clicks.

The original project was Windows-only. This version is ported to Linux (X11) on RHEL 9.

The technology stack — one paragraph each

  • Godot Engine — a free, open-source game engine (think Unity but smaller and FOSS). Dororo is built on Godot 4.4.
  • Godot .NET — a special build of Godot that supports C# scripting. The original project mixes GDScript (Godot's own language) and C# for Windows-specific window manipulation. We have to use the .NET build, not the regular one.
  • GDScript — Godot's built-in Python-flavored scripting language. Most of Dororo's game logic is in GDScript.
  • GDExtension — Godot's plugin mechanism for native C++ libraries. The Live2D plugin uses this.
  • gd_cubism — an open-source GDExtension by MizunagiKB that lets Godot render Live2D Cubism models. We build it from source.
  • Live2D Cubism Native SDK — proprietary SDK from Live2D that gd_cubism links against. It's free for personal use but requires accepting Live2D's license. There is no way around this — Live2D forbids redistributing it.
  • scons — the build system gd_cubism uses. Like make, but Python-based.
  • .NET 8 SDK — for compiling the C# parts of Dororo.

2. Before you start

You need:

  • A RHEL 9 machine (or WSL 2 with RHEL 9). Other recent Red-Hat-family distros (Fedora, AlmaLinux, Rocky) should also work with minor tweaks. Ubuntu/Debian users need to translate the dnf commands to apt.
  • Sudo access for installing system packages.
  • ~5 GB free disk for the toolchain + source + intermediate builds.
  • An internet connection with access to GitHub, the Godot website, and live2d.com.
  • A graphical session if you want to actually see the pet running (X11; see Section 9 for Wayland caveats).

The terminal commands assume you start from your home directory (cd ~). Run each block as-is; lines starting with # are comments you don't have to type.

3. Install system dependencies

These are libraries the build tools and the runtime need:

sudo dnf install -y \
    gcc gcc-c++ git python3-pip unzip \
    dotnet-sdk-8.0 \
    libX11 libX11-devel libXext libXfixes libXrandr libXrender \
    libXcursor libXinerama libXi libGL libEGL \
    fontconfig alsa-lib pulseaudio-libs glib2

What each does:

  • gcc, gcc-c++ — C and C++ compilers, needed to build gd_cubism.
  • git — to clone the gd_cubism source repository.
  • python3-pip — to install scons (a Python package).
  • unzip — to unpack the Cubism SDK.
  • dotnet-sdk-8.0 — to compile the C# parts of Dororo. RHEL 9's AppStream ships this directly; no Microsoft repo needed.
  • libX11*, libXext, libXfixes, etc. — X11 client libraries the Linux/X11 port calls into for click-through and cursor tracking.
  • libGL, libEGL — OpenGL runtime for Godot's renderer.
  • fontconfig, alsa-lib, pulseaudio-libs — fonts and sound (Godot links these even if Dororo doesn't use sound).
  • glib2 — provides gio, used for the Linux trash-bin equivalent.

Now install scons:

pip3 install --user scons
# verify
scons --version | head -2

If scons is reported as "command not found", add ~/.local/bin to your PATH:

echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc
source ~/.bashrc

4. Install Godot 4.4 — the .NET / Mono build

Godot doesn't ship as an RPM. You download a .zip, extract, and run the binary directly. You must use the .NET (also called "mono") build, not the regular Godot — Dororo has C# code that the non-.NET build can't run.

mkdir -p ~/godot && cd ~/godot
curl -LO https://github.com/godotengine/godot-builds/releases/download/4.4-stable/Godot_v4.4-stable_mono_linux_x86_64.zip
unzip Godot_v4.4-stable_mono_linux_x86_64.zip
cd Godot_v4.4-stable_mono_linux_x86_64
# verify the binary works
./Godot_v4.4-stable_mono_linux.x86_64 --version
# expect: 4.4.stable.mono.official.<hash>

Now download the export templates — these are the actual runtime executables that Godot patches your project into when you build a release. They're a separate download.

cd /tmp
curl -LO https://github.com/godotengine/godot-builds/releases/download/4.4-stable/Godot_v4.4-stable_mono_export_templates.tpz
# the .tpz is just a renamed .zip
mkdir -p ~/.local/share/godot/export_templates/4.4.stable.mono
cd ~/.local/share/godot/export_templates/4.4.stable.mono
python3 -m zipfile -e /tmp/Godot_v4.4-stable_mono_export_templates.tpz .
# unzip nests under "templates/", flatten it:
mv templates/* . && rmdir templates
# verify
ls linux_release.x86_64
# expect: linux_release.x86_64

5. Get the Live2D Cubism Native SDK

This is the only step you can't fully automate — Live2D requires you to download their SDK from their website after agreeing to a EULA. The SDK is free for personal / non-commercial use but cannot be redistributed.

Why we need it

gd_cubism is open source, but it links against Live2D's proprietary native libraries (libLive2DCubismCore.so etc.). Without the SDK, the build will fail because the C++ source references symbols that only exist inside Live2D's libraries.

Which version

We need version 5-r.1, not the latest. The gd_cubism source we're building uses functions (GetDrawableRenderOrders, CubismRenderer::Create() with no args) that Live2D renamed in later SDK releases (5-r.5 calls them GetRenderOrders and CubismRenderer::Create(width, height) instead). If you want a newer SDK you'd also have to patch gd_cubism's source.

Download

Live2D's CDN serves all historical versions at predictable URLs:

mkdir -p ~/projects && cd ~/projects
curl -L -o CubismSdkForNative-5-r.1.zip \
    https://cubism.live2d.com/sdk-native/bin/CubismSdkForNative-5-r.1.zip

If you'd rather click through the EULA properly, go to https://www.live2d.com/sdk/download/native/, agree to the license, and download "Cubism SDK for Native 5-r.1" from the past-versions page. Save the .zip somewhere convenient.

6. Build the gd_cubism native plugin

This is the C++ plugin that actually renders Live2D models inside Godot. We clone it, drop the Cubism SDK into its thirdparty/ directory, and run scons to compile.

cd ~/projects
git clone --recurse-submodules https://github.com/MizunagiKB/gd_cubism.git
cd gd_cubism

# extract the SDK into thirdparty/
cd thirdparty
python3 -m zipfile -e ~/projects/CubismSdkForNative-5-r.1.zip .
# you should now have thirdparty/CubismSdkForNative-5-r.1/
ls
cd ..

# build release variant (used by the exported game)
scons platform=linux arch=x86_64 target=template_release -j$(nproc)

# build debug variant (used when you open the project in the Godot editor)
scons platform=linux arch=x86_64 target=template_debug -j$(nproc)

Each build takes 5–15 minutes depending on CPU. When done you'll have:

demo/addons/gd_cubism/bin/libgd_cubism.linux.release.x86_64.so
demo/addons/gd_cubism/bin/libgd_cubism.linux.debug.x86_64.so

If the build fails with errors about GetDrawableRenderOrders or CubismRenderer::Create, you accidentally downloaded a newer Cubism SDK. Delete thirdparty/CubismSdkForNative-*, fetch 5-r.1 specifically (Section 5), and re-run scons.

7. Get the Dororo source

If you have the source tarball that accompanies this guide:

mkdir -p ~/projects/claude
cd ~/projects/claude
tar -xzf /path/to/Dororo-0.3.0-source.tar.gz
ls Dororo-0.3.0/

Or clone from the original upstream and apply our changes manually — but the tarball is much easier.

Either way, you should now have ~/projects/claude/Dororo-0.3.0/ with all the project files.

8. Place the gd_cubism binaries into the Dororo project

The Dororo project's addons/gd_cubism/bin/ is empty (binaries are gitignored upstream). Copy in the ones you just built:

cp ~/projects/gd_cubism/demo/addons/gd_cubism/bin/libgd_cubism.linux.*.x86_64.so \
   ~/projects/claude/Dororo-0.3.0/addons/gd_cubism/bin/

# verify
ls ~/projects/claude/Dororo-0.3.0/addons/gd_cubism/bin/
# expect: libgd_cubism.linux.debug.x86_64.so  libgd_cubism.linux.release.x86_64.so

9. First import + build the C# code

The Godot editor needs to do an initial pass to (a) generate import caches, and (b) build the C# DLL. Run it once headlessly:

cd ~/projects/claude/Dororo-0.3.0
~/godot/Godot_v4.4-stable_mono_linux_x86_64/Godot_v4.4-stable_mono_linux.x86_64 \
    --headless --import

You'll see a flurry of import messages. Some warnings are normal — CubismFramework::Initialize() is complete and Live2D Cubism SDK Core Version 5.0.0 mean the plugin loaded.

Then build the C# DLL:

dotnet build
# expect: Build succeeded. 0 Warning(s). 0 Error(s).

If you see CS errors here, the C# port is broken. Read the error carefully — it'll point to a file and line. The most common cause: missing using System; if you've edited any .cs file.

10. Export the Linux binary

The export preset [preset.1] named "Linux" is already in export_presets.cfg. Run:

mkdir -p export
~/godot/Godot_v4.4-stable_mono_linux_x86_64/Godot_v4.4-stable_mono_linux.x86_64 \
    --headless --export-release "Linux" export/Dororo.x86_64

You should end up with:

export/
├── Dororo.x86_64
├── Dororo.pck
├── libgd_cubism.linux.release.x86_64.so
└── data_Dororo_linuxbsd_x86_64/   (.NET runtime + Dororo.dll)

Verify the .moc3 is packed

This is the gotcha that bit us. The Live2D .moc3 binary file has no Godot importer, so the default export filter silently drops it. The preset uses include_filter="*.moc3" to force-include it. Verify:

python3 -c "
with open('export/Dororo.pck', 'rb') as f:
    print('MOC3 packed:', b'MOC3' in f.read())
"
# expect: MOC3 packed: True

If you ever see False here, the Doro will be invisible (transparent window, no character). Check export_presets.cfg — [preset.1] must have include_filter="*.moc3".

11. Run

cd ~/projects/claude/Dororo-0.3.0/export
./Dororo.x86_64

You should see a transparent borderless window with the Doro character. You can: - Left-click + drag to move her - Middle-click to open a menu - Right-click on her body parts for expression interactions

Errors you can ignore on first launch

xkbcommon: ERROR: ... unrecognized keysym "dead_hamza"

RHEL 9.7's Compose file uses a keysym name xkbcommon doesn't know. Harmless.

WARNING: Your video card drivers seem not to support the required Vulkan version, switching to OpenGL 3.

Godot falls back to OpenGL when Vulkan is missing (common in WSL or on machines without a discrete GPU). Works fine.

ERROR: Couldn't find the given section "system" and key "auto_start" ...

First-launch — there's no config.ini yet. Open settings once and tweak any value to create one; these errors will go away.

12. Wayland vs X11 — important for real desktops

The X11-specific features (click-through, always-on-top, global cursor query, fullscreen detection) only work in an X11 session, not Wayland. Wayland intentionally hides these capabilities from clients.

On RHEL 9 GNOME: at the login screen, click the gear icon and pick "GNOME on Xorg" instead of the default "GNOME". After login, verify:

echo $XDG_SESSION_TYPE
# expect: x11    (NOT wayland)

If you're on Wayland, the app will still run, but the desktop-pet illusion is broken — mouse follow won't track outside the window, click-through won't pass clicks to apps behind, etc.

On WSL2 with WSLg: WSLg uses XWayland (X11 emulation on top of Wayland). Most features work but mouse follow is limited to within the WSL session — moving your mouse over Windows apps won't update Doro's gaze. You'll also see software-rendered OpenGL (Mesa/llvmpipe) which is slower than a real GPU.

13. Common build problems and fixes

Symptom Cause Fix
scons build fails: 'GetDrawableRenderOrders' not a member of CubismModel Wrong Cubism SDK version Re-download SDK 5-r.1 (not 5-r.5+), wipe thirdparty/CubismSdkForNative-*, re-extract
unzip: command not found unzip package missing sudo dnf install unzip
dotnet build error: Environment is an ambiguous reference between 'Godot.Environment' and 'System.Environment' C# namespace collision Fully qualify: System.Environment.GetEnvironmentVariable(...)
Export shows transparent window but no Doro .moc3 missing from pack Check export_presets.cfg [preset.1] has include_filter="*.moc3"; re-export
Window opens, Doro renders, but csmReviveMocInPlace: "size" is invalid errors in console Same as above — .moc3 is empty / missing Re-export with include_filter="*.moc3"
Settings dialog opens but checkboxes don't respond Subwindow focus issue on WSLg / older WMs Make sure project.godot has window/subwindows/embed_subwindows=true
Window won't appear at all Compositor not running, or X session crashed Try gnome-shell --replace (X11) or just relogin
libgd_cubism.linux.release.x86_64.so fails to load: missing libstdc++ Missing runtime sudo dnf install gcc-c++
gio: command not found when using trash drag-and-drop glib2 missing sudo dnf install glib2

14. What we changed vs. the upstream Dororo project

If you're curious what's different from the original Windows project:

  • scripts/cs/Linux/X11Native.cs (new) — X11 P/Invoke helpers (XQueryPointer, XShapeCombineRectangles, EWMH ClientMessage senders, _NET_ACTIVE_WINDOW reader)
  • scripts/cs/WindowManager.cs, MouseTracker.cs, HideTaskBarIcon.cs, FullscreenDetector.cs, FileAPI.cs, AutoStarter.cs — dual-platform via runtime OperatingSystem.IsWindows() / IsLinux() branching. Windows path unchanged; Linux uses X11/EWMH/XDG equivalents.
  • scripts/cs/MouseDetection.cs — viewport-readback click-through toggle Windows-only (it conflicts with sub-windows on Linux X servers; harmless to leave off, you keep clicking the window).
  • scripts/gd/interact/hit_area_handler.gd — fixed a math bug where the wandering Doro's hit detection didn't work when facing right.
  • scripts/gd/ui/setting/setting_window.gd — Settings window grabs focus when opened (needed on some Linux WMs).
  • scenes/main.tscn — LLM-chat feature removed (nodes deleted, load_steps adjusted).
  • prefabs/ui/tool_bar.tscn, scripts/gd/ui/toolbar/toolbar.gd, setting_chat.gd, setting_interact.gd — chat-related wiring removed / nulled out.
  • export_presets.cfg — added [preset.1] "Linux" with include_filter="*.moc3".
  • project.godot — window/subwindows/embed_subwindows=true.

The chat removal is separate from the Linux port; if you want chat back, restore those files from upstream.

15. Editing and re-exporting

Once you've built everything once, the iteration loop is:

  1. Edit .gd or .cs files in your editor of choice (or open the project in the Godot editor at ~/godot/Godot_v4.4-stable_mono_linux_x86_64/Godot_v4.4-stable_mono_linux.x86_64 --path ~/projects/claude/Dororo-0.3.0/).
  2. dotnet build if you changed C# files.
  3. ~/godot/.../Godot_v4.4-stable_mono_linux.x86_64 --headless --export-release "Linux" export/Dororo.x86_64.
  4. ./export/Dororo.x86_64 to test.

.gd (GDScript) changes don't need dotnet build — they're interpreted at runtime from inside the .pck.
